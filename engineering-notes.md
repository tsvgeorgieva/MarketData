# Engineering notes

A living document for the VSG technical assessment. It records the decisions made and how AI was used, so a reviewer can follow the reasoning. Planning is tracked on the GitHub issue map "Wayfinder: VSG assessment implementation spec".

## Decisions so far

| Area | Decision | Why |
| --- | --- | --- |
| Platform | .NET 10 (LTS), C# 14 | Current LTS and already installed |
| Architecture | Clean architecture (Domain / Application / Infrastructure / Api), single ASP.NET Core host running ingestion as a `BackgroundService` plus the API | Simplest deployable unit for the time budget. Splitting ingestion into its own worker is a documented future improvement (independent scaling, isolated failures, no duplicate ingesters when the API scales out) |
| Database | SQL Server (Docker Compose locally, Azure SQL in the proposal), EF Core | Author's experience; first-party EF Core provider; natural fit for the Azure deployment proposal. Cost: large Docker image, amd64-only |
| Collected data | Closed 1-minute klines (`<symbol>@kline_1m`) on one combined Binance stream | All SMA periods (5m, 30m, 1d, 1w) aggregate from 1m candles; order-book and ticker streams are not needed |
| Price | Close of a closed 1m Candle | One definition serves both endpoints |
| 24h average | Simple mean of closed 1m closes over a rolling 24h, partial windows allowed, `404` when there is no data | Plain reading of the assessment; Binance's weighted average and a volume-weighted mean are documented alternatives |
| Precision | `decimal` end to end, results rounded to 8 dp | Binance sends prices as strings; avoids floating-point error |
| SMA window | `s` is the end Reference Instant (omitted = now): the `n` Buckets ending with the one containing `s`. Bucket value = last Candle's close; the in-progress Bucket is included; a Candle counts only if closed by `s` | Trailing SMA is the standard definition and a start that defaults to now would have no data. Departs from the PDF's word "starting", stated in the README |
| SMA alignment and gaps | Everything UTC, weeks start Monday 00:00 (observed on Binance, undocumented). Missing Buckets are not filled; average what exists, `isPartial` when fewer than `n`, `404` when none | Same "average what exists" rule as the 24h average; forward-fill would present uncollected data as real. Forward-fill is a README trade-off |
| SMA API contract | One object (`symbol`, `period`, `requested`, `from`, `to`, `average`, `dataPoints`, `isPartial`, `latestBucketInProgress`); `n` 1..1000 required, `p` one of five values (case-sensitive) required, `s` optional; bad input is `400` ProblemDetails | The PDF says "returns the SMA", singular; strict validation, no silent defaults |
| Symbol management | Admin API `GET` / `PUT /{symbol}` / `DELETE /{symbol}` under `/api/admin/symbols`. A DB table is the source of truth, seeded once from config. Add is validated against Binance `exchangeInfo` (`422`, `503` if Binance REST is down). Changes apply live via an ingestion reconcile loop (desired set in DB vs subscribed set), with an async 24h backfill on add. Removal stops collection but keeps history; reads then return `404`. Idempotent (`PUT` 201/200, `DELETE` 204). Cap of 20 symbols | A typo must not create a symbol that never gets data; reconciling makes failed subscribe frames self-healing and restarts trivial. Purge/retention is a future improvement |
| Admin auth | Static `X-Api-Key` header on `/api/admin/*` only; key from config/env (Key Vault in the Azure proposal) | The PDF asks for no auth, but open admin endpoints would be the first thing a reviewer flags. Entra ID/JWT with roles is the documented upgrade |
| Ingestion pipeline | One combined `kline_1m` stream (`data-stream.binance.vision`, URL built from the DB's Monitored Symbols). Reconnect on `serverShutdown` or any drop with jittered exponential backoff (1s to 60s); no proactive 24h rotation or liveness watchdog. After every (re)connect and symbol add, backfill the trailing 24h from REST klines (subscribe first). Writes are insert-if-absent on `(Symbol, OpenTime)` through a bounded channel and a single batching writer. The reconcile loop diffs the DB against `LIST_SUBSCRIPTIONS`. `/health/live` and `/health/ready` (Binance down = Degraded, DB down = Unhealthy), with reconnect counts tracked | Always backfilling 24h is stateless and heals any hole whatever its cause, at the cost of re-reading ~1,440 rows per symbol per reconnect, acceptable while reconnects are rare. Never overwriting is right because Binance is the only source. The channel keeps a stalled DB from blocking the socket. Rotation, watchdog, a periodic gap scan and metrics are future improvements |
| API surface | MVC controllers with `AddXmlSerializerFormatters` and `ReturnHttpNotAcceptable`: JSON by default, XML only when asked, `406` otherwise. PDF routes kept (`/api/{symbol}/24hAvgPrice`, `/api/{symbol}/SimpleMovingAverage`), admin under `/api/admin/symbols`, health under `/health` outside `/api`. No URL versioning. Dedicated response DTOs shared by both formats | Minimal APIs do not negotiate content, so XML would need hand-built result code. The PDF fixes the paths, so a version prefix would break the contract |
| Error model and validation | Every error is RFC 9457 ProblemDetails (`application/problem+xml` for XML clients), with `traceId`. Check order: key `401`, format `400`, then domain `404`/`422`/`409`. Format rules in the Api layer, symbol rules in one `SymbolCode` value object | One predictable shape for clients in both formats; no validation library for three parameters |
| OpenAPI | Built-in `Microsoft.AspNetCore.OpenApi` plus Scalar UI, always on, including under compose | A reviewer can try the API without extra tooling |
| Hosting and TLS | Container serves plain HTTP on 8080; TLS ends at the ingress in the Azure proposal; forwarded headers are config-gated | Avoids certificate setup in the container with no security gain behind a proxy |
| Logging | Serilog JSON to console; one summary line per request with `traceId`; Binance failures, reconnects, subscription changes and backfills logged by level; bodies off by default behind a config switch | Enough to diagnose the ingester and API without logging secrets or payloads. Configuration and secrets are a separate ticket |
| Data model | `Candles`: clustered PK `(Symbol varchar(20), OpenTime datetime2(3) UTC)`, no surrogate key, no FK, no secondary indexes; `Open/High/Low/Close` `decimal(18,8)`, `Volume` `decimal(28,8)`. Open time is stored (Binance's key), close time is not. A non-minute-aligned open time is stored with a warning, never rejected. `MonitoredSymbols`: `Symbol` PK, `AddedAt`, `RemovedAt`; rows never deleted, so an empty table means first run and `Symbols:Seed` applies | Binance documents only that klines are unique by open time, not that they are minute-aligned; rejecting one would lose data backfill cannot return. The one key serves the 24h seek, the SMA seek and the insert-if-absent lookup |
| Retention | None built; Candles kept forever (about 1 GB a year at 20 symbols) | Small at this scale, and a purge would fight `p=1w` with `n` up to 1000. Sizing in the README; purge is a future improvement |
| Migrations | EF Core migrations applied by `Database.Migrate()` at startup behind `Database:MigrateOnStartup` (on in dev and compose, off in the Azure proposal, which runs an `efbundle` step); compose waits for a SQL Server healthcheck | Single replica, so no migration race; one command to run the demo, and the production path is shown |
| Query design | 24h average: LINQ `COUNT/SUM/MIN/MAX`, C# divides. SMA: one raw SQL query picks the last close per Bucket (`ROW_NUMBER`, at most `n` rows), C# computes alignment and the mean. Rounded once to 8 dp, `AwayFromZero`. Candles are written by `OPENJSON` plus `NOT EXISTS (UPDLOCK, HOLDLOCK)`, batch de-duplicated in C#, inserted count returned | Calendar logic lives in one place; no millions of rows pulled for long Periods; one explicit rounding rule. `MERGE` and `IGNORE_DUP_KEY` rejected (concurrency history; hides duplicates) |
| Console client | Separate thin project MarketData.Client that knows only the public HTTP contract (own DTOs, HttpClient, System.CommandLine). Commands: vg24h <symbol>, sma <symbol> -n -p [-s], symbols list/add/remove. API URL from --url, then MARKETDATA_URL, then http://localhost:8080; admin key from MARKETDATA_API_KEY or --api-key, never stored or printed. Human text by default; --json / --xml print the raw body. ProblemDetails shown as one stderr line with 	raceId; exit codes 0 ok, 1 API error, 2 usage/config, 3 unreachable. About 1 hour, lean tests | The PDF only asks for the same price analysis through the HTTP API. A separate project proves the contract stands alone; the admin wrappers are cheap and make the demo run from the client. Day-1 budget was spent on planning, so polish is cut |
| Deployment | Written Azure proposal plus working `docker compose up`; no real cloud deploy | Time budget (about 10-12 hours) |

Open decisions (solution structure, configuration and secrets) are tracked as tickets on the map. Vocabulary is in [GLOSSARY.md](GLOSSARY.md); plain-language background is in [docs/primer-market-data.md](docs/primer-market-data.md); sourced research is in [docs/research/](docs/research/).

## Future improvements

Deliberately not built, to keep the required scope clean within the time budget. Each item says what it would buy and where the decision to defer was made. Items are added as tickets defer them.

| Improvement | What it would buy | Deferred in |
| --- | --- | --- |
| Run ingestion as a separate worker service | Scale the API and the ingester independently, isolate failures, and avoid duplicate Binance connections when the API scales out | Architecture decision |
| Real Azure deployment and CI/CD pipeline | Repeatable releases and a live environment; the written proposal plus `docker compose up` cover the assessment | Map scope |
| Periodic reconciliation scan for missing minutes | Heals holes older than the 24h backfill window, for example after a long outage | SMA contract, ingestion pipeline |
| Backfill from the last stored candle (plus the scan) | Less re-reading per reconnect than always fetching 24h; worth it only if reconnects turn out to be frequent | Ingestion pipeline |
| Proactive, make-before-break rotation of the 24h connection | No gap at Binance's connection limit | Ingestion pipeline |
| Liveness watchdog on the socket | Detects a silently stalled connection that never closes | Ingestion pipeline |
| Metrics export (reconnect counts, backfill duration, lag) | Alerting and dashboards instead of only logs and `/health/ready` | Ingestion pipeline |
| Pick up corrected klines (upsert instead of insert-if-absent) | Stored candles follow any correction Binance publishes | Ingestion pipeline |
| Entra ID / JWT with roles for the admin API | Per-user identity, auditing and revocation instead of one shared API key | Symbol management |
| Purge or retention policy for removed symbols and old candles (time-based job, per-symbol purge) | Bounded storage growth | Symbol management, data model |
| Pre-aggregated rollup tables for long-Period SMAs | Constant-time `1w`/`1d` queries instead of scanning 1m rows on demand; not needed at about 10M rows | Data model |
| Per-bucket series in the SMA response | Lets a client chart the data points behind the average | SMA contract |
| Optional forward-fill of missing buckets | A gap-free series for consumers who prefer it, clearly labelled as filled | SMA contract |
| Volume-weighted or Binance-weighted 24h average | An average that reflects trading activity rather than time | Price and 24h average semantics |
| Nested routes `/api/symbols/{symbol}/...` | The naming the author would prefer; the PDF fixes the current paths | API surface |
| API versioning (URL or header) | Room for breaking changes without breaking clients | API surface |
| Pagination of the symbol list | Only needed if the cap of 20 is lifted | API surface |
| Rate limiting (built-in limiter, per client IP, `429`) | Protects the API and database from abusive clients | API surface |
| Short-lived response and output caching (`Vary: Accept`) | Fewer database hits, since answers change at most once a minute | API surface |
| ETags and conditional requests | Bandwidth savings for repeat callers | API surface |
| Console client polish: dotnet-tool packaging, config file, retries, shell completion, tables/colour output | A friendlier client for daily use; not needed to show the contract | Console client |

Not yet discussed, listed on the map as candidates: wider observability beyond the health endpoints and logs. CORS is deliberately not planned: this is a public API, not a browser app.

## AI usage

AI assistance: Claude Code (Claude Sonnet 5.5) in the desktop app, using the `research`, `wayfinder`, `grilling` and `domain-modeling` skills from Matt Pocock's skills collection (plugin `mattpocock-skills`, v1.3.1), published through [AI Hero](https://www.aihero.dev) ([skills newsletter](https://www.aihero.dev/s/skills-newsletter), [source repository](https://github.com/mattpocock/skills)). These skills shaped the workflow: research delegated to background agents against primary sources, a shared decision map on GitHub Issues, and decisions made through numbered questions with recommended answers. The AI was used for reading and research, structuring decisions, and drafting documents. Decisions were put to the author as numbered questions with a recommended answer; the author accepted, changed or rejected each. Nothing below has been compiled into the final build yet.

### Corrections and caveats worth knowing

- While testing GitHub access, the AI accidentally created a throwaway test issue on the repository. It was noticed straight away and deleted; nothing else was affected.
- Research agents flagged parts of their findings as unverified (Binance connection limits, some XML serializer details, hosted-service behaviour in `WebApplicationFactory`, the Testcontainers SQL Server defaults). These are to be checked by a spike before being relied on.
- The AI's reading of the assessment PDF came from decoding its text streams; some punctuation was garbled, and the author should re-check any wording that matters against the original.
